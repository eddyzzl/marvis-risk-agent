# V2 批量模型验证规格

## 1. 目标与产品边界

批量模型验证是模型验证之外的独立首屏入口，用于一次登记并顺序运行 1–10 套模型材料。它复用单模型验证的扫描、Notebook 执行、PMML 对比、确定性指标和报告链，不建立第二套验证算法。

批次的职责是编排、隔离、恢复和汇总：

- 每套材料创建独立的 `validation` 子任务，保留各自的状态、合同、证据、Word 报告和 Excel 分析报告。
- 父任务只保存批次成员关系、整体进度和汇总 Excel，不把单模型事实压平为自由文本。
- 子任务按创建顺序逐项执行；当前版本不并行运行 Notebook，也不共享中间结果。
- 单个子任务失败不得阻断后续子任务；成功或需人工复核的子任务在重试时不得重复执行。
- 批次不自动确认任何输入合同，不自动选择模型，不把 OOT KS 排名解释为冠军，也不替代独立验证人员结论。

## 2. 创建合同

`POST /api/validation-batches` 接收一个批次名称、验证人员和 1–10 个 item。每个 item 必须显式提供：

- 模型名称与可选版本、算法、目标列、分数列、切分列和时间列；
- 一个受允许根目录约束的材料目录；
- Notebook、样本、PMML 和数据字典四个明确文件角色。

平台必须对路径做规范化和材料角色校验。同一批次内任意两个角色不得复用同一个文件路径，避免子任务之间产生隐式所有权。创建失败时不保留半个父任务或孤立的批次目录。通用单任务创建、扫描、材料修改和删除接口不得绕过批次成员关系。

当前批次运行模式固定为 `agent`，但这里的 Agent 只负责单模型报告文案等既有受控环节；指标、状态和最终批次 outcome 由平台代码确定。

## 3. 状态机与确认门

父批次状态：

```text
created -> running -> awaiting_confirmation -> running
                                      \-> completed
                                      \-> partial_failure
                                      \-> failed
```

第一次启动按 ordinal 扫描所有可运行子任务。需要用户确认的子任务进入 `awaiting_confirmation`；父任务在本轮完成后停在同名状态并释放 `active_job_kind=validation_batch`。前端必须在父任务工作区内打开明确绑定到 child task id 的输入合同，逐项提交。只有服务端确认所有待确认合同均为 `ready` 后，父任务才能再次启动。

运行期间，父任务的 `active_job_kind` 必须保持 `validation_batch`。详情轮询先看到终态、但父任务 job 尚未关闭时，前端不得提前清除 busy 状态、恢复删除按钮或启动重复 job；job 关闭后才以服务端父任务状态为准。

## 4. 执行、失败隔离与恢复

合同 ready 的子任务复用单模型验证的可恢复阶段：

1. `scan`
2. `pmml_scoring`
3. `metrics`
4. `report_conclusion`
5. 单模型报告完整性核验

每个 item 的 stage、错误代码和经过边界处理的公开错误文案独立持久化。异常只将当前 item 标为 `failed`，循环继续下一项。批次从 `partial_failure` 或 `failed` 重新启动时，仅失败项按已记录阶段回退到最近安全状态；`succeeded` 与 `review_required` 项只重新认证报告完整性，不重跑计算。

进程在 queued job 尚未开始或运行中意外退出时，startup recovery 必须结束活动 job、释放父任务 busy 状态，并把批次收敛到可解释且可重试的失败状态。公开错误不得泄漏受允许材料根目录之外的绝对路径。

## 5. 结果与下载合同

每个完成 item 保留现有单模型下载地址：

- `validation_report.docx`：Word 验证报告；
- `validation.xlsx`：结构化分析与指标报告；
- 父任务内的人工复核深链，定位到对应 child row。

所有 item 结束后，父任务原子生成 `validation_batch_summary.xlsx`。汇总只消费已持久化的子任务结果，不重算指标，至少包含 ordinal、模型名称/版本、OOT KS（只展示）、OOT PSI、PMML 状态、压力风险、单模型报告完整性、确定性 outcome、人工复核链接和失败摘要。

批次终态规则：

- 全部 item 通过或仅需人工复核：`completed`；父任务有复核项时为 `review_required`。
- 至少一个失败、但并非全部失败：`partial_failure`，父任务为 `review_required`。
- 全部 item 失败，或汇总报告生成失败：`failed`。

无论批次终态为何，已经成功生成的单模型报告都必须保留。汇总失败不得删除或覆盖这些报告。

## 6. 前端交互合同

- 欢迎页使用独立“批量模型验证”卡片和创建对话框，不复用单模型创建表单。
- 创建表单明确展示 1/10 上限、四个材料角色、逐模型上传状态和失败原因；任一模型上传失败时不得提交批次创建。
- 父任务显示总状态和逐 item 状态、stage、合同状态、结果、错误及下载按钮。
- URL `?task=<parent>&item=<child>` 只聚焦并滚动到匹配行，不把 child 提升为左侧当前顶层任务。
- 运行、暂时网络错误、输入确认和终态使用同一个 dedicated poll controller；不得同时启动单模型 report poll。
- 删除、通用扫描或通用材料修改不得破坏父子 membership。

## 7. 安全与验收

发布前至少验证：

- schema 拒绝 0、超过 10、额外字段和不完整材料；
- 路径边界、符号链接输出目录、重复材料路径和公开错误脱敏；
- 多 item 固定顺序、单项失败继续、部分失败只重试失败项；
- 合同永不自动确认，未全部 ready 时 start 失败关闭；
- 单模型 Word/Excel 全部保留，汇总 Excel 可下载且不重算确定性指标；
- 父任务 active job 生命周期、崩溃恢复和重复启动冲突；
- 宽桌面真实浏览器完成创建、确认、运行、逐项下载、汇总下载、刷新和深链恢复。

真实材料、独立验证签字、原生 Windows 文件占用和生产调度不由本规格的合成测试或本地浏览器纵切证明。
