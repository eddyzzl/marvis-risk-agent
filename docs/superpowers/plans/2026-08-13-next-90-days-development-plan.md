## 2. 需要你做的（Part A，详细）

### A-1 · 三个月范围收口决策 —— P0 / Q3 / 第 1 周

**为什么**：失败风险 #1 是范围失控。roadmap 里 V2.x 还挂着 SQL 接入、完整 Strategy Workbench、组织与生产治理、调度告警、实时评分、决策引擎对接等大量范围；90 天不可能全收口，必须由你做产品决定，而不是让我默认全冲。

**三个选项**（我的推荐是①）：

1. **① 本地纵深 + 差异化（推荐）**：90 天只做——外部校准（T4-2/T4-3）+ 代码健康（拆分/清理）+ SQL 只读接入 + 策略能力补齐（历史回溯/额度定价/泄漏检测）+ 反事实沙箱首屏。生产治理、SSO、跨设备全部明确不做。
   - 理由：没有试点客户之前，生产治理是"对着空气做产品"；反事实沙箱+可审计证据链才是能打动真实机构的差异化。
2. **② 生产化冲刺**：90 天主攻 RBAC、逐环境晋级/回滚、实时评分、调度值班。
   - 风险：全部生产能力没有真实客户验收，容易变成另一个"本地完整、生产未证"的矩阵行。
3. **③ 双线并行**：①+② 各做一半。
   - 风险：正是 Q3 失败风险 #1 的形态，不建议。

**交付物**：一份你签字的「90 天范围声明」（我可以起草选项分析文档），明确：做 / 不做 / 暂缓列表。写完后我同步更新本计划与 roadmap 的当前状态段。

**需要你做的**：

2. 预登记基准参数并签字确认：split 方式、随机 seed、特征清单、训练预算、容差（我按你的决定固化到 harness，之后不可随意改）。
3. 人工审阅最终基准报告并确认「两个数据集均通过」。

**我可以做的**（B-3）：补齐 harness 的登记/对比/报告环节，跑数、出证据。签字与数据集获取由你负责。

**需要你做的**：

**时间点**：第 8 周敲定意向即可，材料对账（A-3）在第 12 周与其一起完成。SQL 接入（B-7）的优先级与试点机构的数据形态直接相关，所以 A-6 要早做。

4. 验收：单元 + API + Agent 自然语言"连接 X 库的 Y 表做 Z 分析" + 浏览器纵切；写入 capability-status 对应行（数据接入从文件扩展为文件+SQL）。

2. 选择偏差检测：审批总体 vs 风险总体的分布对比（现有双人群 SampleDesign 基础上加诊断层）。
3. 全部为**诊断证据**，不自动拒绝流程；用户确认后可作为报告章节。

### B-10 · 额度/定价 typed 影响口径 —— P1 / Q6 / 第 10 周

**做法**：ImpactCube 现有 approval/reject 口径外，补 limit/pricing/segmentation 的 typed 影响：额度变化 → 敞口/EAD/EL 增量；定价变化 → 收益/坏账权衡；分群×月矩阵。沿用现有「缺口径澄清、暂缺留空、fail closed」契约。

### B-11 · 反事实沙箱（Q4 的差异化功能）—— P1 / Q4 / 第 12 周首屏纵切

**为什么**：这是我认为能让项目行业领先的功能——把已存在的 `decision_twin/`（本地 CAS、Champion/Challenger 约束、proposal-only 桥）产品化。

**形态**：用户对已认证的策略/模型提出"假如"（额度阈值 +10%、拒绝率降到 30%……）→ 平台在受治理样本上有界反事实重放 → 确定性输出通过率/坏率/EL/限额利用率/分群×月 → 与真实回测证据**分开标注**的"假如"审计报告。

**做法**：
1. 先把 decision_twin 的反事实重放内核接到 packs/strategy 的 ImpactCube 数据链上（有界、确定性、不保存逐行客户明细）。
2. 加 typed request 编译与 PlanValidator 接入（自然语言与 Manual 双入口，沿用现有 compiler）。
3. 首屏纵切：一个"假如"问题走通「提问 → 计划 → 执行 → 证据 → 下载」。
4. 验收：unit + API + Agent + 浏览器纵切；capability-status 的「信用决策数字孪生」行从"无 API/UI"更新为有首屏纵切（仍明确标注无生产接入）。

### B-12 · 兼容层口径回归加固 —— P1 / Q1 / 第 8 周

**做法**：针对 V1/V2 双轨的坏样本极性、人群语义、空标签策略、样本 ref 四字段等历史事故点，补一组**跨版本交叉契约测试**（同一输入在 legacy 与 native 路径下必须产出文档承诺的相同/明确不同结果），把 roadmap 里"必须/禁止"条款逐条变成测试断言。这是对 Q1"兼容层最不自信"的直接回应。

### B-13 · 架构文档与知识外化 —— P2 / Q2 / 随 B-4 滚动

**做法**：新增 `docs/architecture.md`（模块边界、数据流、每个 workflow 的端到端链路、兼容边界清单），不复制 roadmap；随 B-4 拆分滚动更新。目标：降低 bus factor，让新读者不需要人肉解释 AGENTS.md 里的隐含约定。

### B-14 · 公平性/拒绝原因证据链最小纵切 —— P2 / Q6 / 第 11 周
