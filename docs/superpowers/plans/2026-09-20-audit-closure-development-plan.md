## 1. 开发目标与完成定义

目标：让本轮发现的确定缺陷、评测失真、架构耦合、未接通能力和业务验收缺口都有实现、反例测试及可复核证据；再次进行源码审计时，不再以同样原因发现这些问题。

交付后的产品应使一名具备业务判断能力的负责人，在应用内完成数据准备、标签、特征、建模、验证、策略、历史效果对账、参考环境部署及监控，不依靠开发者修改数据库、补脚本或手工修复任务。发布审批仍由独立身份承担。

三个完成节点必须分别验收：

| 节点 | 必须达到的结果 | 不能代替的结果 |
| --- | --- | --- |
| S：软件交付 | 确定性算法、真实 Agent/Tool、UI、标准启动、本地真实决策服务、调度、部署与回滚全部接通；软件负例通过 | 不能证明任意机构接入或实盘收益 |
| H：历史业务验收 | 在用户提供的脱敏历史数据中，完成可支持的业务任务、时间核验、成熟结果对账和受限效果分析 | 不能恢复原本不存在的时间戳、拒绝标签、动作记录或实验分配 |
| P：指定业务线生产验收 | 指定机构接口、身份、发布、监控和通知接通，经过批准的试运行及成熟期业务评估 | 不能由本地参考服务、mock、历史回放代替 |

**全部计划完成 = S、H、P 均通过。** 当前可以开展 S，并在数据接收后开展 H；P 的接口和现场条件尚未具备，必须保留为待完成项。只完成 S 或 H 时必须按该节点名称交付，不宣布整个计划完成。

“本轮问题关闭”不等于宣称任意任务 100% 自治、任意数据无风险、永无新缺陷或已经行业领先。可通过开发消除的是明确缺陷和证据缺口；数据不可识别性、随机模型表现和未来业务分布变化必须被检测、量化及约束，不能隐藏。

## 2. 保留不变量

1. 全部工作属于 V2.x；不把当前范围移到未来 major，也不新增第二套 Agent、Skill、策略 DSL 或指标 runtime。
2. 复用 Plugin / Tool / Hook / Workflow、PlanValidator、PlanExecutor、ToolRunner、canonical DSL、现有仓储与 artifact 事务。
3. 保持 V1 兼容工作流、手动与 Agent 模式、四个 `RMC_*` 必填契约、Notebook 内存评分与提交 PMML 的比较语义。
4. 数据字典 `importance` 保持必填；模型指标由确定性代码计算；LLM 和记忆不能修改指标、执行回执或成功状态。
5. 保留 invocation receipt、输入/输出/manifest hash、数据绑定、修订检查、过期确认防护和 maker/checker 职责分离。
6. 保持单模型/多模型报告数量、模型独立进度、草稿编辑、失败隔离与取消行为。报告文本修订不重跑评分。
7. 历史 plan、artifact、API 和导出格式采用版本化迁移；不得把旧的未验证证据自动升级为已通过。
8. 保留现有 dirty/untracked/ignored 工作。禁止为重构清空 workspace、迁移旧证据 hash 或修改历史结果。
9. 前端验证按宽桌面 1440/1600/1920 CSS 像素实施，不扩展到移动端项目。
10. 脱敏样本仍按受控数据处理：默认不提交仓库、不写进提示或日志；模型只接收必要 schema、聚合结果及脱敏证据引用。

## 5. 工作包

### WP00：冻结验收范围、历史数据能力与兼容台账

责任：技术负责人 + 业务负责人；先做范围和数据核验，不调整业务数据。

实施：

1. 建立现有入口→Workflow→Tool→产物→证据→支持限制的源码清单。记录动态注册、字符串调用、外部导出、兼容 facade 和测试独用符号。
2. 盘点用户历史数据：稳定脱敏关联 ID、申请/决策/事件/可得时间、版本、实际动作、标签及成熟日期、现金流、成本、设备/关系边、催收动作等。
3. 对每个问题输出“可证明 / 可计算但依赖假设 / 当前无法回答”；绑定数据 hash、字典版本、时间语义和授权使用范围。
4. 数据按时间与业务主体划分开发、验证、封存验收集；拟合变换和选参不能读取封存数据。Agent 任务另分开发集、固定回归集、最终隐藏验收集；最终任务及答案由独立验收者持有，不用于日常实现调试。脱敏不能破坏跨表关联、顺序及成熟窗口。
5. 冻结业务目标、正常审批与修复干预定义、支持范围、数据规模、模型 profile、时间/token/成本预算、在线负载/SLO、恢复目标。未填写的预算不能自动视为不限或零。
6. 记录兼容 API、历史产物及 Notebook/报告/批次的黄金样例。为每个工作包分配代码所有者和独立验收者。

主要已有边界：`marvis/domain.py`、`packs/strategy/project_context.py`、`data/contracts.py`、`repositories/*`、`orchestrator/eval/*`。

出口：数据清单和支持集有版本，台账 F01–F22 均有工作包；时间、动作或现金流缺失会准确降低可证明范围；不得补造可得时间、拒绝样本标签或分配概率。真实数据未提供时此项 H 部分保持待完成。

### WP01：修正评测口径并建立联合基准骨架

主要文件：`marvis/orchestrator/eval/{contracts,runner,scoring,cases,cli}.py`、`orchestrator/planner.py`；复用 `tests/test_orch_eval*.py`、`test_eval_cli.py`、已有真实模型触点测试。

实施：

1. 分开契约回归、盲测规划、真实执行三类评测；强制记录真实/fixture 模型和工具、是否经过真实 Executor。
2. `expected` 仅交给评分器。盲测输入中的业务约束必须独立声明来源，并经生产相同解析路径进入模型；保留生产安全约束。
3. fixture 不再产出能满足真实执行门槛的 DONE；缺 fixture 输出必须显式未建模或失败。旧报告缺证据类别时按未获证明展示。
4. 联合 runner 通过真实 API、PlanDriver、PlanExecutor、ToolRunner 执行，不复制执行逻辑，不直接改 DB 状态或注入结果。
5. 记录每次 run 的 commit、环境、模型、数据 hash、提示版本、调用/token、重试、干预、分阶段时间、失败及成本来源。
6. 新增失败归档与回归集；失败修复后产生新 run，原始分母不能被覆盖。能力校准不得只用契约回归成绩。
7. 实现证据 schema 和关闭校验器：强制证据层、环境种类、数据来源、目标环境身份、commit/数据/口径绑定、原始回执及独立复核。参考环境不能满足 P，合成数据不能满足 H，模型自述不能满足任何执行凭证。
8. 日常基线只使用开发/回归集。最终隐藏任务失败后保留原分母，将已公开失败纳入回归；独立验收者追加新的未见同类任务，并同时重跑原集及新增集。不能把旧集逐题修满后单独宣称泛化通过。

验收：只改变 expected，模型可见请求和上下文不变；expected 随机哨兵不能进入路由、规划、压缩、重试、replan 或记忆；模拟、skip、评分器异常不能被算作真实成功；工具认证和授权负例仍全部阻断。

2. 实现历史案件/动作/回收/成本的样本、时间与成熟契约，支持策略比较、预算、净回收和不确定性分析。
3. 本地真实参考执行器完成排队、分案/动作、回执、取消与重启恢复；机构执行器复用部署/动作幂等和审批机制。
4. 回流付款、冲销、分期兑现及回收成本，避免重复记账；无对照证据时不声称动作导致增量回收。
5. 工作台贯通方案→审批→执行→结果→调整；个人联系/真实外发动作只在明确批准范围内执行。

验收：重复事件/重试不重复分案或执行；不合政策的渠道/时段/频次阻断；动作成本、付款冲销、分期和净回收金标准通过；源码没有以无条件 unsupported 代替已承诺能力。没有动作/成本/回收历史时 H 不能通过，机构执行验证在 WP16。

### WP15：独立软件、历史数据和业务负责人全旅程验收

1. 独立验收者从正常安装启动应用，使用封存数据和任务集，覆盖手动/Agent、单模型/多模型及新增业务路径。
2. 用户作为主要操作者，仅做正常业务说明与必要审批；任何临时补脚本、改数据库、开发者提示或修参数救场均记录为修复干预。
3. 分别核验完成率、证据正确率、业务判定、干预次数、人工有效操作时间、总耗时及失败恢复；有可比人工基线时才报告效率提升。
4. 正式跑第 6 节全部门槛、宽桌面真实后端浏览器旅程、真实 PMML、历史产物兼容、取消/恢复/升级回滚及性能预算。
5. 第二位审查者只看当前源码、测试与原始运行产物，逐项重做 F01–F22 检查；不把本计划或功能说明当成通过证据。
6. 对新发现先判影响，涉及本轮关闭条件或严重回归时修复后重验；保留失败运行和签字记录。

S/H 节点交付：源码版本、机器可读报告、测试日志、UI 证据、产物 hash、数据可证明范围、完整失败/skip/unknown 清单、未完成 P 项目。WP16 未完成时不得在台账把 P 置通过。

### WP16：指定机构接入和成熟期业务验收

当前外部依赖：机构/供应商 API 契约、测试环境、凭据提供方式、身份映射、业务动作权限、SLO、通知渠道、允许试验的风险预算及成熟周期。

实施：

1. 为首个指定业务线选择真实适配器，完成 conformance 和现场联调；其他机构不能继承这个通过结论。
2. 在授权范围内先影子/小流量试运行，核验数据可得性、特征一致、决策流水、部署/回滚、通知、恢复和职责分离。
3. 由业务负责人确定风险/收益基准及退出条件；实验须记录分流概率和分配版本。没有受控实验条件时只报告适用的观察证据。
4. 等待相应标签/现金流成熟，比较预期与实际并做偏差分析；策略效果不佳时维持或回滚，不能把“功能正常”当作“业务有效”。
5. 完成生产运维责任、事件处置与恢复演练后，由业务、技术、独立审批主体签字关闭 P。

出口：指定业务线全部适用 P 验收通过，缺接口、缺成熟结果、业务效果不符合目标或职责分离未落实均保持未完成。此包不设虚构完成日期，不因 S/H 已完成自动放行。

业务结果要求针对最终申请投产的方案，不要求每个候选都盈利。正确识别并否决不达标候选属于软件能力通过，但不能记为该方案业务达标。最终没有可达标方案时应交付真实限制和处置结果，不承诺通过编码必然改善经济收益。

## 6. 正式验收门槛

以下是计划拟采用的首版门槛，不是已测成绩。业务目标、成本/延迟预算及数据规模在 WP00 冻结；后续更改必须形成新基准版本并保留旧结果，不能为一次失败临时放宽。

### 6.1 联合 Agent 基准

- 最终隐藏基础集至少 100 个任务，与开发/固定回归集分开：64 个应完成任务（数据处理、标签、特征、建模、验证、策略、风险/组合、监控 8 类各 8 个），20 个应澄清/拒绝的边界任务，16 个应成功恢复任务。每个 case 在运行前冻结预期结果类型。
- 新增在线决策生命周期、连接器/反欺诈、催收三个扩展族各至少 10 个应完成任务，每族无修复干预完成率至少 95%（正好 10 个时必须 10/10），另补各自安全/证据负例；软件总验收不得漏掉。改变样本数时最低成功数取 `ceil(0.95 × 分母)`。
- 基础正常任务无修复干预完成率至少 95%（64 个中至少 61 个），每个基础业务族至少 7/8；正常审批不算修复，但必须记录。扩展族独立计分，不用基础集掩盖新功能失败。澄清/拒绝任务不得计入“业务完成率”分子。
- 20 个边界任务全部正确；涉及授权、时间穿越、证据绑定、假完成、重复副作用的严重错误必须为 0。
- 可确定性恢复的故障注入契约全部通过；真实模型恢复任务同时报告恢复成功率，门槛至少 95%（16 个时必须 16/16），不能用“安全停止”替代原本应恢复的任务。
- 冻结至少 20 个关键正常任务，每个重复 3 次：报告全部 60 次，完成率至少 95%，严重安全/证据错误为 0；完整报告每族结果和 95% 置信区间。
- 观察成功率不等于已经证明总体成功率达到该值；不采用“100 个任务过 95 个所以任意业务 95% 成功”的说法。
- 人工等待、LLM、工具、排队分别计时；报告 p50/p95、调用/token、重试/replan、超限、成本未知与全部失败。至少一个声明支持的真实模型 profile 完成全套验收；其他模型只继承自己实际通过的范围。
- expected、评分标准和封存答案与运行上下文隔离；不得污染 Agent 记忆。所有平台 receipt、API 和执行后检查正常启用。
- fixture 替换、skip、预算超限、环境失败和评分失败均保留在原始分母并分别列明，不算成功；无效验收运行可重建，但原运行不能删除。任何新基准版本必须与前版结果并列，说明新增或变更原因。

### 6.2 数据、业务与输出

- 日期/币种/单位/分母/客群/目标极性/成熟度/采用版本完全绑定；错误绑定负例全部被拦截。
- 未知 available_at、缺拒绝标签、缺动作/现金流、缺实验概率均能解释并阻断相应声明，不能填默认值凑通过。
- 输入、假设、策略或样本版本变化会使不再适用的旧验收显式失效。
- 手工金标准与平台指标一致，数值容差逐指标冻结，不以统一宽容差掩盖差异；报表/图/界面从同一结构化事实生成。
- XLSX/DOCX/Notebook 需检查内容与实际载体；可下载、可打开、字段和分箱正确，不以文件存在或 HTML 字符串存在替代。

### 6.3 架构与恢复

- 六个确认残留清除；指定两个 exec 共享命名空间移除；指定重复业务 helper 和四处编排收敛。
- 每个公共兼容入口有支持责任与测试；临时桥有删除条件，不能新增一批永久兼容债务。
- validation 的指定 DB/任务/渲染副作用移出；前端任务状态只有明确所有者；正常/恢复事件契约一致。
- CI 对模块依赖、指定旧机制、危险重复和关键行为设置针对性检查，不以总行数或任意函数长度作为合格标准。
- 实际 crash/restart、重复请求、部分写入、通知失败、外部成功本地失败均有故障演练；未知副作用状态不能自动重发。

### 6.4 运行与生产

- 标准启动可配置使用真实参考决策服务、内置监控及本地通知，不依赖测试注入。
- 参考环境与机构环境身份分离；实际部署、回滚及监控状态必须有目标环境回执。
- SLO 在固定硬件/版本/负载下测量；冷启动、持续运行、并发和恢复分别报告。没有 SLO 或只有 mock 压测不能通过。
- 生产完成需要指定机构、真实接口与成熟业务证据；没有这些条件的项使用 `awaiting_external`，绝不标 `closed`。

## 7. 实施与检查方式

实施授权：用户已于 2026-09-20 明确要求“开始开发吧”。按工作包进行本地实现与验证；不因实施授权自动执行外部通信、上线或业务实验。

每个工作包顺序：核对基线与 dirty 状态 → 对可观察缺陷建立必要反例/行为基线 → 小范围实现 → 最小相关验证 → 受影响验证 → 提交证据。低影响残留删除不新增“函数已删除”一类镜像测试。

本机命令约定：

```bash
# 单包：替换为该包实际受影响路径；不执行占位参数。
conda run -n py_313 python -m pytest -q <相关测试路径>
conda run -n py_313 python -m ruff check <受影响Python路径> --extend-exclude '*.ipynb'
node --check <受影响JS文件>
git diff --check

# 阶段关闭：工作区 diff 或显式 CHECK_DIFF_RANGE 必须覆盖本阶段所有提交。
conda run -n py_313 bash scripts/check --affected-full

# 最终软件关闭：准备好 Java、Notebook kernel、浏览器及依赖后，运行完整门。
MARVIS_RUN_PLAYWRIGHT_SMOKE=1 conda run -n py_313 bash scripts/check
```

上述完整门仍不能代替新增真实模型/业务基准。新 runner 的 CLI 参数在 WP01 实现时定义，不能把尚不存在的命令写成已可运行。最终需单独保存真实模型、真实历史数据及现场验收报告；测试 skip 不等于相应证据通过。

阶段门通过后不无故反复跑全量；只有新修改、失败或真实疑点扩大验证。文档改动至少 `git diff --check`。公开发布和 tag 沿用 `scripts/release_push.py`，本计划不自动授权发布。

并行与回滚：

- 后端模块化、前端会话整理、数据时间契约可由不同所有者推进；`app.py`、`domain.py`、DB schema、manifest 及 API schema 有单一合入负责人。
- 每个迁移包保留旧数据读取能力和可回滚步骤；恢复旧代码不能要求删除新业务数据。先做备份和迁移试跑，处理不可逆 schema 差异。
- 不以撤掉 receipt、减少确认绑定、忽略不可用指标或放宽失败状态的方式修复回归。

## 8. 验收证据与防复发

实施时新增机器可读 run report（路径由 WP01 定义），至少包含：

`run_id / finding_ids / work_package / evidence_tier / environment_kind / source_kind / target_id / commit / dirty_state / model_profile_hash / dataset_hashes / input_hashes / criterion_version / expected_isolation / real_executor / tool_receipts / artifact_hashes / test_counts / failed / skipped / intervention_counts / timing / usage / unknowns / independent_review / evidence_paths`。

WP01 的关闭校验器必须校验枚举和证据绑定：`reference_runtime` 不能满足 P；`synthetic_fixture` 不能满足 H；P 必须绑定指定机构环境和真实操作回执；A 必须有真实模型、Executor 和工具凭证。`closed` 的原始证据缺失、层级不足、哈希失配、独立复核未通过均返回拒绝。JSON 台账本身不作为这些条件已满足的证明。

秘密和原始个人记录不能写入报告；引用必须能在授权环境内回查，不能用不可审计的自然语言“已通过”代替日志。

台账状态流转：`planned → in_progress → ready_for_review → closed`；也允许 `failed` 或 `awaiting_external`。`closed` 需要全部 required evidence tiers，且每层都有原始证据、时间和独立审查结论。部分已通过只更新对应证据，不关闭整个条目。

复审必须包含：

1. F01–F22 每项重新定位源码与调用链，核对原问题确已消失。
2. 运行指定反例与真实旅程，检查未换成另一种等价缺陷。
3. 检查缺失、skip、未知与外部依赖是否完整暴露；比较支持集和原分母，防止通过改口径“消除问题”。
4. 检查新增重构桥、重复状态、字符串测试及未接入模块是否形成新债务。
5. 独立列出 S/H/P 当前结论。只有所有适用门槛通过才允许宣称整个计划完成。

## 9. 开始实施时的第一批任务

1. 完成 WP00 数据字段/可证明范围清单及冻结验收配置。
2. 实施 WP01 的 expected 隔离、证据类别与真实 runner 基线。
3. 并行实施 WP02：KS 参考核边界修复、六个前端残留与无效断言清理、转换闭包去重。
4. 基线和第一批回归稳定后进入 WP03，再推进真实模块化与状态整理。

当前不需要先获取生产接口才能开始上述工作。WP13/14/16 所需的供应商契约、事件/动作数据和现场条件按台账逐项取得；缺少它们不阻塞独立的软件工作，也不构成对应问题已关闭的理由。
